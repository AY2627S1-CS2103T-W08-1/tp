Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PatientListPanel, PatientDetailPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The main window shows two panels side by side:

  • PatientListPanel shows the displayed patient list, with one PatientCard per patient. It observes Logic#getFilteredPatientList(), so it updates when the list is filtered or changed.
  • PatientDetailPanel shows the full details of the patient being viewed, including their medications, allergens, care instructions, contacts and appointments. It observes Logic#getViewedPatient() and redraws itself whenever that value changes, showing a placeholder message when no patient is being viewed. See the view patient feature for how the viewed patient is set and cleared.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Patient objects from the model.

Logic component

API : Logic.java

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. If the command changed the patient data, LogicManager saves it through Storage. Before executing the command, it takes a Model.Snapshot of the patient data, the patient list filter and the viewed patient. If the save fails, it restores the Model from the snapshot and reports the failure, so a command reported as failed leaves no change that would be lost on restart. Commands that change no patient data, such as list or exit, are not saved, so they still work when the data file is read-only.
  5. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

How the parsing works:

  • Command words are matched case-sensitively by AddressBookParser; field prefixes are also case-sensitive. Both use lowercase spellings. For example, LIST produces Unknown command. rather than running list.
  • When called upon to parse a user command, the AddressBookParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The AddressBookParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.
  • Field parsers use ArgumentTokenizer#verifyNoInvalidPrefixes before tokenization, declaring their free-text prefixes separately from their supported prefixes. Non-reserved slash text such as and/or, mg/ml, and x/123 is allowed within those fields. Preambles and structured fields retain strict unknown-prefix checks. CliSyntax#RESERVED_PREFIXES contains all field prefixes, including ones unsupported by the current command; update this set when adding a prefix. Reservation checks lowercase candidates with Locale.ROOT, so wrong-case reserved prefixes are rejected with the existing unrecognized-parameter message. Tokenization still recognizes only the exact lowercase prefix. Literal N/A (optionally followed by punctuation) remains allowed in free text. Existing standalone slash-word exceptions and their punctuation corrections still apply. The validator also checks the first value word attached to a recognized prefix, carrying its free-text context but allowing no nested field prefixes: a/x/123 is text, whereas a/p/123 is rejected. This nested validation cannot recurse again because its set of valid prefixes is empty. Context switches follow tokenization's space boundary, so a tab does not create a free-text field. Tokenization itself is unchanged.

Model component

API : Model.java

The diagram below shows the Patient class in more detail.

The Model component,

  • stores the patient data, i.e., all Patient objects (which are contained in a UniquePatientList object).
  • stores the Patient objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Patient> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores the patient being viewed, if any. It exposes this patient as an ObservableValue<Patient> that the UI observes, so the detail panel updates when the viewed patient changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Patient records: Each Patient is composed of Name, Nric, Dob, Phone and Address values (one of each), an archived flag, and lists of care information, as shown in the second diagram:

  • zero or more Medication objects, each with a description and a list of daily times (LocalTime),
  • zero or more Contact objects, each with a name, role, phone and note,
  • zero or more Appointment objects, each with a date, time, provider and note, kept sorted by date, then time,
  • allergens and careInstructions, which are plain String lists.

These lists default to empty and are defensively copied with List.copyOf, so callers cannot modify them through the getters. Updating a patient creates a replacement Patient, which the model stores using setPatient. The diagram leaves out the constraints of each value class and the exceptions of UniquePatientList.

Archived patients: An archived patient stays in the UniquePatientList. ModelManager only changes which patients its filtered list shows, using Model#PREDICATE_SHOW_ACTIVE_PATIENTS or Model#PREDICATE_SHOW_ARCHIVED_PATIENTS.

Duplicate identity: Patient.isSamePatient compares NRIC values. Nric stores input in uppercase, so NRIC identity is case-insensitive. UniquePatientList rejects patients with the same NRIC; different patients can share a name.

Storage component

API : Storage.java

The Storage component,

  • can save both patient data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

The patient data is saved in data/mediconnect.json and the user preferences in preferences.json, both relative to the folder the app is launched from. MainApp sets these paths when the app starts.

JsonUtil#saveJsonFile() writes both files through FileUtil#writeThroughTemporaryFile(): the JSON is written to a new temporary file in the same folder, which then replaces the file in one step. A save that fails partway, e.g., on a full disk, therefore leaves the last complete file in place, and the temporary file is deleted. An existing file that cannot be written to, e.g., because it is read-only, is not replaced, although on macOS and Linux its folder may let the temporary file take its place.

JsonUtil#readJsonFile() reads both files, and backups for restore. It reads the text with FileUtil#readFromFile(), which decodes it as strict UTF-8: a byte that is not valid UTF-8 makes the read fail, instead of being replaced by � and then saved into patient data. JsonUtil then ignores a UTF-8 byte-order mark at the start of the file, which some editors add when saving as UTF-8. It rejects a file with anything other than whitespace after its JSON data, so that text added to a file by mistake is not silently dropped on the next save.

Before mapping the JSON to objects, JsonUtil also rejects a file in which a name or a text value has half of a surrogate pair on its own. Only a JSON escape of a surrogate, such as \ud800, in a hand-edited file can give such text. It cannot be written as UTF-8, so the next save would silently turn it into ?.

As the diagram shows, JsonSerializableAddressBook holds a list of JsonAdaptedPatient objects, and each JsonAdaptedPatient holds lists of JsonAdaptedMedication, JsonAdaptedContact and JsonAdaptedAppointment objects. Each patient is saved with its name, NRIC, date of birth, phone number and address as strings, its allergens and care instructions as lists of strings, and an archived flag. A medication is saved with its description and its times as HH:MM strings. A contact is saved with its name, role, phone and note, and an appointment with its date, time, provider and note. The list of patients is saved under the JSON key persons, kept from AB3. When the file is read, JsonAdaptedPatient#toModelType() validates patient fields and converts medications, contacts and appointments using their model constraints. If any patient, medication, contact or appointment is invalid, two patients share an NRIC, a patient has duplicate contacts or appointments, or an allergen or care instruction is blank or duplicated, the whole file is rejected. Care-entry duplicates ignore letter case and whitespace differences, as the care commands do.

JsonAddressBookStorage reads the file with JsonUtil#readJsonFileStrictly(), which also rejects a property that the JSON class does not have, e.g., a misspelled careInstructons, and a property given twice. Ignoring them, as Jackson does by default, would drop their values without a warning the next time the data is saved. An unknown property is reported as invalid data that names it, while its value is not shown, since it can be patient data. preferences.json is still read leniently, so that a file from an older version keeps its known settings.

On a DataLoadingException, MainApp copies the unreadable file beside the original as mediconnect-unreadable-<UUID>.json before creating an empty model. The copy uses no replacement option, so an existing recovery file is never overwritten. The UI shows its absolute path and failure details in a startup warning. JsonSerializableAddressBook#toModelType() prefixes validation failures with the one-based entry position in the JSON persons array, including null entries and duplicate patients, while preserving the original exception as the cause. The first invalid entry is reported. Both startup and restore use these diagnostics. MainApp shows validation messages for IllegalValueException causes; other read failures receive a generic format/permissions message rather than raw parser exceptions that can include file contents. Later commands save normally to the original data path. If preservation fails, the exception stops initialization before commands can overwrite the file. MainApp#init() records this IOException instead of letting JavaFX abort initialization. MainApp#start() then uses UiManager#showStartupError() to show an error dialog without a main-window owner, on the JavaFX application thread, before exiting. The dialog names the data-file path and distinguishes a directory path, denied access, and other preservation failures without displaying raw parser exceptions. The dialog and exit actions can be supplied through a package-private constructor for tests. A regression runs the real startup-error method and checks that the error is presented before exit; the UI tests cover the dialog. No model, logic or main window is created after a preservation failure, and stop() skips preference saving when there is no model. JSON validation stays in storage; startup recovery stays in MainApp.

Implementation

This section describes some noteworthy details on how certain features are implemented.

View patient feature

The view INDEX command shows the full details of a patient in the PatientDetailPanel, next to the patient list.

Implementation

ModelManager keeps the patient being viewed in an ObjectProperty<Patient>. It is exposed through Model#getViewedPatient() and Logic#getViewedPatient() as a read-only ObservableValue<Patient>, whose value is null when no patient is being viewed.

The sequence diagram below shows how view 1 goes through the Logic component.

  1. ViewCommandParser parses the index in the same way as DeleteCommandParser, so view accepts the same INDEX values as delete.
  2. ViewCommand#execute() checks the index against the filtered patient list. An index beyond the list size produces the same invalid-index message as delete.
  3. ViewCommand calls Model#setViewedPatient() with the selected patient.
  4. PatientDetailPanel listens to Logic#getViewedPatient() and redraws itself whenever the value changes. It shows a placeholder message when the value is null, and None recorded for an empty medication, allergen, care instruction, contact or appointment list. Each entry is shown on one line by PatientFormatter#toSingleLine(), which exported records also use, so that a line break stored in a hand-edited entry cannot look like another numbered entry.

ModelManager keeps the viewed patient consistent with the address book:

  • setPatient(target, editedPatient) replaces the viewed patient with editedPatient if target is being viewed, so the panel shows changes such as newly added care information. If the change archives the viewed patient, as archive does, it clears the viewed patient instead.
  • deletePatient(target) clears the viewed patient if target is being viewed.
  • setAddressBook(...), which clear confirm and restore use, clears the viewed patient unless the new data has the same patient with the same details.

Filtering the patient list (e.g., with find) does not change the viewed patient.

Since the viewed patient can be filtered out of the list, PatientDetailPanel also observes Logic#getFilteredPatientList(). Under the name, it shows the viewed patient's one-based index in that list, which is the INDEX that commands use, or Not in the displayed list, and updates it whenever the list or the viewed patient changes. When it shows a patient with a different NRIC from the last one shown, it scrolls back to the top, so that the new patient's name is visible. The same patient redrawn, e.g., after addcare, keeps the scroll position.

The panel numbers the appointments with upcoming ones first, then past ones, in the order that cancelappt and editappt also use. Upcoming and past are decided at the time the patient was last shown, which Model#getAppointmentsOrderedAt() returns, so the numbers do not change when an appointment passes while the patient is shown. Logic#getAppointmentLinesAsShown() reads that time once, and uses it both to order the appointments and to mark each past one with (past) through PatientFormatter#formatAppointments(). PatientFormatter#formatRecord(), which the export command uses, calls the same method with the time of the export, so an exported record words appointments the same way as the panel.

Design considerations

Aspect: Where the viewed patient is stored

  • Alternative 1 (current choice): In the Model, as an observable value.
    • Pros: Commands that change patients can keep the panel up to date without knowing about the UI. The behavior can be unit tested in ModelManagerTest.
    • Cons: Adds a small amount of UI-related state to the Model.
  • Alternative 2: Return the patient in CommandResult and let MainWindow update the panel.
    • Pros: The Model stays unchanged.
    • Cons: The panel would show stale data after the patient is edited or deleted by another command.

Aspect: How past appointments are shown

  • Alternative 1 (current choice): Keep one numbered list and add (past) after each past appointment.
    • Pros: The numbers that cancelappt and editappt use stay in one list, so the panel and an exported record stay easy to read.
    • Cons: The mark adds a little text to each past appointment.
  • Alternative 2: Split the list under Upcoming and Past headings, as listappt INDEX does.
    • Pros: Past appointments are grouped visibly.
    • Cons: One numbered list split across two headings can be read as two lists, each starting from 1..

Clearing all patients

AddressBookParser delegates clear arguments to ClearCommandParser. It accepts only the lowercase confirm token, with surrounding whitespace allowed. Missing confirmation or extra arguments produce a ParseException with the warning and command format before any data is changed.

ClearCommand#execute() first calls BackupCommand#execute() to save all current data using the existing backup implementation. A backup failure propagates as a CommandException before the model is changed. Only after the backup succeeds does it replace the entire address book with an empty one through Model#setAddressBook(), including archived patients and patients hidden by a filter. The existing model logic clears the viewed patient. The success message includes the backup location. LogicManager saves the change and restores its snapshot if saving fails; the automatic backup remains available. Backups include archived and filtered-out patients, even for an empty address book, and can be recovered with restore.

Edit patient feature

The edit INDEX [n/NAME] [ic/NRIC] [dob/DOB] [p/PHONE] [a/ADDRESS] command replaces one or more core details of a patient in the displayed list while preserving all care-related data and state.

Implementation

The sequence diagram below shows the successful execution of edit 1 p/91234567. Error paths are omitted for clarity.

  1. EditCommandParser parses a positive patient index and the supplied fields. It requires at least one field, rejects repeated or unsupported reserved prefixes, and uses the same field and slash-text rules as add.
  2. EditCommand#execute() resolves the index against the filtered patient list and creates an immutable replacement using the supplied values and the existing values for omitted fields.
  3. The replacement preserves medications and their times, allergens, care instructions, contacts, appointments, and archived state. A changed NRIC is rejected if another patient already has it.
  4. The command stores the replacement with Model#setPatient(patient, editedPatient), then resets the displayed list to active patients, or archived patients when the edited patient is archived, with Model#updateFilteredPatientList(...).
  5. Model#setViewedPatient(editedPatient) shows the edited patient. The PatientDetailPanel listeners redraw its details and displayed index.

Design considerations

Aspect: Preserving fields that edit cannot change

  • Alternative 1 (current choice): Build the replacement through Patient#withDetails(...).
    • Pros: The model owns the copy logic, so care-related fields and state are preserved in one place.
    • Cons: The helper must be updated whenever Patient gains another field.
  • Alternative 2: Construct a replacement directly in EditCommand.
    • Pros: Avoids a model helper used by one command.
    • Cons: Repeating the full constructor in the command makes it easier to drop an unrelated field during editing.

Add care info feature

The addcare INDEX [med/MEDICATION]... [al/ALLERGEN]... [ci/CARE_INSTRUCTION]... command appends care information to a patient in the displayed list.

Implementation

The sequence diagram below shows the successful execution of addcare 1 med/Metformin. Error paths are omitted for clarity.

  1. AddCareCommandParser parses a positive index and the values supplied under med/, al/, and ci/. At least one care prefix is required, and every entry must be non-blank.
  2. AddCareCommand#execute() resolves the index against the filtered patient list, trims each entry, and compares it case-insensitively with entries in the same category.
  3. The command appends only unique entries, creates a replacement immutable Patient, and calls Model#setPatient(patientToEdit, editedPatient).
  4. If the edited patient is currently being viewed, ModelManager#setPatient() also updates viewedPatient. The observable listener then causes PatientDetailPanel to redraw immediately with the updated care information.

Each skipped duplicate is named in the command feedback. The command distinguishes an entry already stored for the patient from an entry repeated earlier in the same command. Unique entries are still added; if every supplied entry is a duplicate, the command fails without changing the patient.

Design considerations

Aspect: Appending or overwriting care information

  • Alternative 1 (current choice): Append new entries to the patient's existing care information.
    • Pros: Existing medication, allergen, and instruction records are preserved, reducing the risk of accidental data loss.
    • Cons: Correcting or removing an existing entry requires a separate command in a future version.
  • Alternative 2: Replace the full list whenever a care category is supplied.
    • Pros: Users could correct or remove entries with the same command.
    • Cons: Users would need to re-enter every value they want to keep, making accidental data loss more likely.

Aspect: Handling duplicate entries

  • Alternative 1 (current choice): Skip trimmed, case-insensitive duplicates and continue adding other unique entries. Feedback names each skipped entry and whether it already existed or was repeated in the command.
    • Pros: Valid new information is retained even when the same command contains duplicates.
    • Cons: The success result can contain both an added-entry summary and duplicate warnings.
  • Alternative 2: Reject the entire command when any duplicate is found.
    • Pros: The operation has simpler all-or-nothing behavior.
    • Cons: One duplicate prevents all valid new entries in the same command from being added.

Backup and restore feature

The backup command saves a copy of all patient data to the data/backups folder, and restore FILENAME replaces all patient data with one of those copies.

Implementation

BackupCommand#saveBackup(ReadOnlyAddressBook) writes the given data to a new temporary file in the backup folder through JsonAddressBookStorage, the same class that saves data/mediconnect.json, then renames it to the backup's name and returns the path of the file. A backup that fails partway therefore never leaves a cut-off file under a backup's name, and FileUtil#deleteTemporaryFile() removes the temporary file. On macOS and Linux, a new temporary file can be opened only by the current user, and the backup keeps that when it is renamed. The file is named after the current time, as mediconnect-YYYYMMDD-HHMMSS.json. If a file with that name already exists, -1, -2 and so on are added to the name, so no backup is overwritten. Checking whether a name is free and then saving under it are two steps, so two backups made at the same moment, e.g., in two MediConnect windows, or by restore or clear confirm while a backup is made, could otherwise choose the same name, and one would replace the other. BackupCommand#saveUnderNextFreeName() therefore does both while it holds a FileLock on the empty file .backup.lock in the backup folder, which makes backups in other processes wait. A process can hold that lock only once, so the backups of one MediConnect also take turns through a synchronized block first. BackupCommand#execute() calls saveBackup with the data in the Model and reports the path. If the file cannot be written, Messages#describeWriteFailure() turns the IOException into a short reason for the error message.

The sequence diagram below shows a successful restore old.json.

  1. RestoreCommandParser returns a ListBackupsCommand if no FILENAME is given. It lists the .json files in data/backups by the time they were last changed, newest first, so that the user can copy a name. Files changed at the same time, e.g., after being copied together, are listed by name, last first, with numbers compared by value, so that -10 comes before -9. Otherwise, it checks that FILENAME is only a file name: it must not contain /, \ or :, must not be . or .., and must be a name the operating system accepts. This keeps restore inside data/backups on every operating system.
  2. RestoreCommand#execute() first finds the file. If no file has the given name, but one with .json added does, e.g., for restore mediconnect-20261020-083015, it restores that file, and its messages give that file's name. It reads the whole file through a JsonAddressBookStorage for that file, which checks every patient the same way as loading data/mediconnect.json at startup. A missing file, a file that MediConnect is not allowed to read, a damaged file and a file with invalid data each make the command throw a CommandException with its own message, before anything is changed.
  3. Only then does the command back up the current data, by calling saveBackup on a BackupCommand with the same clock and folder. If that fails, nothing is restored.
  4. The command replaces the data with Model#setAddressBook(), which also clears the viewed patient unless the restored data has the same patient with the same details, and shows the active patients again with Model#updateFilteredPatientList(). The result gives the number of patients restored, how many of them are archived, since only active patients are then listed, and the path of the automatic backup.
  5. As after every command that changes the patient data, LogicManager then saves the Model, which replaces data/mediconnect.json.

Both commands have a second constructor that takes a java.time.Clock and the backup folder. The usual constructor passes the system clock and data/backups, while tests pass a fixed clock and a temporary folder, so that file names and folders are predictable.

Design considerations

Aspect: Keeping the current data safe during a restore

  • Alternative 1 (current choice): Check the whole backup first, then back up the current data automatically, and only then replace it.
    • Pros: A missing or invalid backup never changes the current data, and any restore can be undone by restoring the automatic backup it reports.
    • Cons: Every restore adds a file to data/backups.
  • Alternative 2: Ask the user to confirm the restore, and keep no automatic backup.
    • Pros: No extra files.
    • Cons: Adds a step to every restore, and a restore confirmed by mistake cannot be undone.

Aspect: What a backup copies

  • Alternative 1 (current choice): Save the patient data currently loaded in MediConnect, through JsonAddressBookStorage.
    • Pros: Needs no changes to LogicManager or Storage, and every backup holds valid data in the current format.
    • Cons: If data/mediconnect.json could not be loaded at startup, a backup holds the empty data MediConnect started with, not the unreadable file. MainApp already keeps that file as a recovery copy at startup.
  • Alternative 2: Copy data/mediconnect.json byte for byte.
    • Pros: An unreadable data file is kept, for repair by hand, although the startup recovery copy already does this.
    • Cons: The path of the data file would have to be passed from Storage through LogicManager to the command, and a backup could hold data that restore then rejects.

Export feature

The export INDEX command saves the full record of a patient in the displayed list to a text file in data/exports, for printing or for handing over, e.g., during a hospital visit.

Implementation

  1. ExportCommandParser parses the index in the same way as ViewCommandParser. ExportCommand#execute() checks it against the filtered patient list, so export exports an active patient after list or find, and an archived patient after listarchived.
  2. ExportCommand#createRecord() builds the lines of the record: a title, Exported on with the date and time from the command's Clock, a blank line, then the lines from PatientFormatter#formatRecord(). These are the patient's name, the details from PatientFormatter#formatDetails(), with Status: Archived for an archived patient, and each list under its heading, numbered by PatientFormatter#formatEntries(). Appointments are ordered and marked (past) at the time of the export, through the same PatientFormatter#formatAppointments() that the detail panel uses.
  3. The file is named after the patient's NRIC, e.g., S1234567A.txt. Before writing, ExportCommand#writeRecord() creates the folder if it does not exist, and throws an AccessDeniedException if an earlier export of the patient is read-only, since the new record would otherwise replace it although the user made it read-only.
  4. The record is written through FileUtil#writeThroughTemporaryFile(), as backups are, so a failed write never leaves a partial record in place of an earlier one, and on macOS and Linux, only the current user can open the file. If writing fails, Messages#describeWriteFailure() turns the IOException into a short reason for the error message.
  5. The command does not change the Model. It logs only the export folder, not the file, since the file name is the patient's NRIC. The date is formatted with Locale.ROOT, so that it uses the digits 0 to 9 whatever the computer's language settings are.

Like BackupCommand, ExportCommand has a second constructor that takes a java.time.Clock and the export folder, which tests use to get a predictable date and folder.

Design considerations

Aspect: How the exported file is named

  • Alternative 1 (current choice): After the patient's NRIC, e.g., S1234567A.txt.
    • Pros: NRICs are unique, and only use letters and digits, which every operating system allows in file names. Exporting the same patient again replaces their earlier record, so the folder holds one up-to-date record per patient.
    • Cons: The file name shows the NRIC. If the NRIC is changed, e.g., with edit, the earlier file is left behind under the old NRIC.
  • Alternative 2: After the patient's name and the time of the export.
    • Pros: The name is easier to recognize, and earlier records are kept.
    • Cons: Names can contain /, e.g., in s/o, which file names cannot, and two patients can have the same name. Every export adds another file.

Aspect: How the record is worded

  • Alternative 1 (current choice): Reuse PatientFormatter, which also words the detail panel.
    • Pros: The wording is defined in one place, so an exported record always reads the same as the panel.
    • Cons: A wording change meant for one of them also changes the other.
  • Alternative 2: Format the record separately in ExportCommand.
    • Pros: The record can be worded differently from the panel.
    • Cons: The same wording is written twice, and the two can drift apart.

Help window

The help command, F1 and the Help menu open the HelpWindow, which lists every command with its format and a one-line description under group headings, below a link to the User Guide.

Implementation

  1. HelpCommand#execute() returns a CommandResult that asks the UI to show help, and MainWindow#handleHelp() shows the help window if it is not already shown. The Help menu item, whose shortcut is F1, calls handleHelp() directly. It then calls requestFocus() on the main window, so that the user can keep typing commands while the help window is open. A minimized help window still counts as shown, and bringing it back from the Dock or the taskbar would move the focus to it, so handleHelp() hides it and shows it again instead. HelpWindow#show() first clears the minimized state, which a window hidden while minimized would otherwise keep.
  2. The list is HelpCommand#COMMAND_SUMMARY, built once from each command's COMMAND_WORD or COMMAND_FORMAT and the prefixes in CliSyntax, which the parsers also use. A renamed command word or prefix therefore also changes the help text. HelpCommandTest checks that every command is listed once, in order, and that AddressBookParser parses every listed format, filled in with sample values, into that command.
  3. MainWindow makes the main window the owner of the help window, so that the help window closes and minimizes with it. An event handler on the help window's own stage hides it on Esc, and each time the help window is shown, it adds the same handler to its owner as an event filter. A filter is used because it sees Esc before the focused command box does. It also keeps itself in front of other windows only while it or its owner has the focus, through a BooleanBinding on both windows' focusedProperty(). The binding is kept in a field, since the properties it observes refer to it only weakly. When the help window is hidden, the filter is removed and the owner's focus is no longer followed.

Design considerations

Aspect: Keeping the help window in view while typing commands

  • Alternative 1 (current choice): Keep the help window in front only while MediConnect has the focus.
    • Pros: The list stays above the main window while the user types commands, but goes behind other apps, e.g., a browser with the User Guide open.
    • Cons: Needs a binding on the focus of both windows, and an Esc filter on the main window.
  • Alternative 2: Keep the help window always in front.
    • Pros: Needs only one call to setAlwaysOnTop(true).
    • Cons: The help window also covers other apps until it is closed.

Contact management

Contact is immutable and contains a name, role, phone and optional note (stored as an empty string when absent). Names are nonblank free text because contacts can be people or organisations, such as Tan & Partners Clinic. They deliberately do not use patient Name constraints. Contact phones likewise have their own rules so clinic and international numbers work without weakening patient-phone validation. Contact#isValidPhone() requires 3 to 15 digits, permits spaces and hyphens, and allows at most one leading + after trimming. The digit bounds are named constants in Contact. Both contact parsers and JsonAdaptedContact use this model validation, so the same limits apply to add, edit, startup loading and restore. Formatting and duplicate identity are unchanged.

Patient keeps an immutable contact list in insertion order. withContacts replaces only that list; addcare copies it when rebuilding a patient. Contact rejects Unicode-whitespace-only names and roles, normalizes name whitespace to single ordinary spaces, and trims role boundaries. Contact identity compares names ignoring case and normalized whitespace, and phones ignoring spaces and hyphens, while retaining +. The model rejects duplicate identities within a patient.

The three contact parsers use the shared prefixes in CliSyntax. Add and edit declare names, roles and notes as free text for slash validation; phones remain structured. Repeated and unsupported reserved prefixes are rejected. Standalone s/o, d/o, c/o, a/l and a/p remain explicit exceptions, ignoring case. Contact validation and the add/edit parsers use StringUtil#stripUnicodeWhitespace() to trim Unicode boundaries, including no-break spaces. The helper scans non-whitespace runs and preserves internal text. Notes from commands use this helper; stored notes are preserved when loading. Edit uses Optional<String> to distinguish an omitted note (preserve) from a present empty note (clear). Commands use displayed patient indices and contact indices from the detail panel. They validate indices and duplicates before calling Model#setPatient. After updating the patient, each contact command calls Model#setViewedPatient(editedPatient), so the panel shows the affected patient even if another patient was previously viewed or the panel was empty. The existing viewed-patient listener refreshes the panel; commands do not access UI controls. The patient-list filter is retained. Rejected commands do not change the viewed patient. If saving fails, the existing LogicManager snapshot restores the patient data, filter and previously viewed patient.

JsonAdaptedContact saves the four contact fields. Missing contact lists load as empty, and missing notes load as empty strings. Null entries, invalid fields and duplicate identities reject the data file with a reason. PatientDetailPanel numbers contacts in insertion order and shows None recorded for an empty list.

Add appointment feature

The addappt INDEX d/DATE t/TIME w/WITH [nt/NOTE] command adds an appointment to a patient in the displayed list.

Implementation

The sequence diagram below shows the successful execution of addappt 1 d/2027-11-05 t/09:30 w/Dr Tan. Error paths are omitted for clarity.

  1. AddApptCommandParser requires d/, t/ and w/ once each, with w/ and nt/ declared as free text for slash validation. It parses the index, the date, the time (with ParserUtil#parseTime, as for medication times) and who the appointment is with, and creates the Appointment toAdd, with an empty note if nt/ is not given.
  2. AddApptCommand#execute() resolves the index against the filtered patient list. It rejects toAdd if the patient already has an appointment at the same date and time with the same person, ignoring case and extra spaces.
  3. The command creates a replacement immutable Patient with toAdd added, which keeps its appointments sorted by date, then time. Model#setPatient() stores it, and Model#setViewedPatient() shows it in the detail panel, so the new appointment and its number can be checked.
  4. The command adds a note to the result if toAdd is in the past, and a warning for each of the patient's other appointments at the same date and time. The current time comes from a java.time.Clock given to the command: the system clock by default, and a fixed one in tests, so that the tests do not depend on when they run. Appointment#isBefore ignores seconds, so an appointment in the current minute is not in the past.

Design considerations

Aspect: Appointments in the past or at the same time as another

  • Alternative 1 (current choice): Add the appointment, with a note or a warning in the result.
    • Pros: A caregiver can record a visit that already happened, or two appointments at the same time, e.g., with a doctor and a nurse together.
    • Cons: A mistyped date is only flagged, not prevented, so the user has to read the result.
  • Alternative 2: Reject such appointments.
    • Pros: A mistyped date or time cannot be saved.
    • Cons: Past visits could not be recorded, and genuine overlapping appointments would need a workaround.

Due medication feature

The due [INDEX] command lists the medication times of today, for all active patients or only for the patient at INDEX in the displayed list.

Implementation

The sequence diagram below shows the successful execution of due 1. Error paths are omitted for clarity.

  1. DueCommandParser accepts either no arguments or a single positive index; anything else throws a ParseException with the usage message of due. It creates a DueCommand with a java.time.Clock from Clock.systemDefaultZone(), and with the index if one was given.
  2. DueCommand#execute() chooses the patients to list. With an index, it resolves the index against the filtered patient list. Without one, it takes every patient in the address book, so that a find does not hide a dose. Archived patients are always left out.
  3. It reads the current time as LocalTime.now(clock), cut to the minute, and turns every time of every medication into a dose. The doses are sorted by time, then by patient name, then by NRIC.
  4. It writes one line per dose, as HH:MM NAME: DESCRIPTION, and adds (earlier today) to a dose whose time is before now. If there are no doses, it returns No medications are due today., or No medications are due today for NAME. when an index was given.

due does not change the patient data, so LogicManager does not save after it.

Design considerations

Aspect: Where the current time comes from

  • Alternative 1 (current choice): DueCommand receives a Clock, as AddApptCommand does.
    • Pros: Tests pass a fixed clock, so the marking of earlier doses does not depend on when the tests run.
    • Cons: Every constructor takes one more parameter, and DueCommandParser has to create the clock.
  • Alternative 2: DueCommand calls LocalTime.now() itself.
    • Pros: Simpler constructors.
    • Cons: Tests of the (earlier today) marking would pass or fail depending on the time of the day.

Aspect: Which patients are listed without an index

  • Alternative 1 (current choice): All active patients, not only the displayed ones.
    • Pros: The caregiver sees every dose due today, even after a find or after listarchived.
    • Cons: The result can differ from the patients shown in the list.
  • Alternative 2: Only the displayed patients.
    • Pros: The result always matches the list.
    • Cons: A dose can be missed because an earlier find is still in effect.

[Proposed] Undo/redo feature

Proposed Implementation

The proposed undo/redo mechanism is facilitated by VersionedAddressBook. It extends AddressBook with an undo/redo history, stored internally as an addressBookStateList and currentStatePointer. Additionally, it implements the following operations:

  • VersionedAddressBook#commit() -- Saves the current address book state in its history.
  • VersionedAddressBook#undo() -- Restores the previous address book state from its history.
  • VersionedAddressBook#redo() -- Restores a previously undone address book state from its history.

These operations are exposed in the Model interface as Model#commitAddressBook(), Model#undoAddressBook() and Model#redoAddressBook() respectively.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The user launches the application for the first time. The VersionedAddressBook will be initialized with the initial address book state, and the currentStatePointer pointing to that single address book state.

Step 2. The user executes delete 5 command to delete the 5th person in the address book. The delete command calls Model#commitAddressBook(), causing the modified state of the address book after the delete 5 command executes to be saved in the addressBookStateList, and the currentStatePointer is shifted to the newly inserted address book state.

Step 3. The user executes add n/David …​ to add a new person. The add command also calls Model#commitAddressBook(), causing another modified address book state to be saved into the addressBookStateList.

Note: If a command fails its execution, it will not call Model#commitAddressBook(), so the address book state will not be saved into the addressBookStateList.

Step 4. The user now decides that adding the person was a mistake, and decides to undo that action by executing the undo command. The undo command will call Model#undoAddressBook(), which will shift the currentStatePointer once to the left, pointing it to the previous address book state, and restores the address book to that state.

Note: If the currentStatePointer is at index 0, pointing to the initial AddressBook state, then there are no previous AddressBook states to restore. The undo command uses Model#canUndoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

Step 5. The user then decides to execute the command list. Commands that do not modify the address book, such as list, will usually not call Model#commitAddressBook(), Model#undoAddressBook() or Model#redoAddressBook(). Thus, the addressBookStateList remains unchanged.

MediConnect is primarily for chronically ill patients and family caregivers in Singapore who coordinate care for elderly or chronically ill patients. Community nurses conducting home visits are a secondary user group. A typical user:

Non-Functional Requirements

  1. MediConnect must operate as a single-user application. Its data file must not be accessed by another user during regular operation.
  2. MediConnect must work on Windows, Linux, and macOS computers with Java 25 installed.
  3. MediConnect must be distributed as a single JAR file of no more than 100 MB and must not require an installer.
  4. MediConnect must store its data locally in a human-editable JSON text file that can be edited in a standard text editor. If the edited file is invalid, MediConnect must start with no patients, keep a copy of the unreadable file, and show a warning with the copy's path and failure details, including the file entry position for patient validation errors. If the recovery copy cannot be created, it must instead show a startup error and exit without changing patient data.
  5. MediConnect must not use a database management system.
  6. MediConnect must not depend on a team-owned remote server for its essential features and must remain usable without an Internet connection.
  7. MediConnect should complete common commands, including listing, finding, adding, editing, and deleting records, and due, and update the displayed results within one second when managing up to 100 patient records, each with up to 10 medications, on a computer with a 4-core CPU and 8 GB of RAM.
  8. A user who types at least 60 words per minute should be able to add a patient, add a medication and delete a patient each in under 30 seconds using commands.
  9. MediConnect's GUI should work without resolution-related inconvenience at resolutions of 1920x1080 or higher with 100% or 125% display scaling. All functions must remain accessible at resolutions of 1280x720 or higher with display scaling up to 150%.

Glossary

  • Allergy: A harmful reaction a patient has to a substance, such as a drug or a food. Each allergy is recorded by the name of the substance that causes it (the allergen), e.g., Penicillin.
  • Appointment: A scheduled visit by a patient to a healthcare provider, recorded with its date, time, and provider. Notes on what was discussed can be added after the visit.
  • APPT_INDEX: The number shown beside an appointment in the numbered appointment list of the patient's details, starting from 1. Upcoming appointments come first, then past ones. editappt and cancelappt use it, together with the patient's index, to refer to an appointment. It stays the same until the patient is shown again, even after an appointment passes.
  • Archive: To remove a patient's profile from the active patient list while keeping all of its records for future reference. Unlike deleting, archiving does not remove any data.
  • Care handover: The transfer of responsibility for a patient's care from one person to another, e.g., from the main caregiver to a relative while the caregiver is travelling.
  • Care information: The care-related records in a patient's profile, i.e., allergies, medications, care instructions, appointments, and contacts. It does not include the patient's basic details.
  • Care instruction: A routine care task that does not involve medication, e.g., "check blood sugar before breakfast".
  • Caregiver: A person who uses MediConnect to coordinate a patient's care, typically a family member of the patient. A caregiver is not necessarily a healthcare professional.
  • CLI (Command Line Interface): A way of using an application by typing text commands rather than by clicking on elements with a mouse.
  • Community nurse: A nurse who cares for patients through scheduled home visits.
  • Contact: A person or organisation linked to a patient's profile, which is either a healthcare provider (e.g., a GP, specialist, or pharmacist) or an emergency contact.
  • Daily time: A time of day, in 24-hour HH:MM format, at which a patient takes a medication every day, e.g., 08:00. A medication can have any number of daily times, or none.
  • Display scaling: An operating system setting that enlarges text and other on-screen elements by a percentage (e.g., 125%) to make them easier to read.
  • Dose: One daily time of one medication of one patient. due lists one line for each dose.
  • Emergency contact: A person to notify in an emergency involving the patient, such as a family member. An emergency contact is not involved in the patient's medical treatment.
  • Expert user: A user who is familiar with MediConnect's commands and prefers to complete tasks using as few commands as possible.
  • GUI (Graphical User Interface): The visual part of MediConnect, consisting of windows, lists, and panels that display information to the user.
  • Human-editable text file: A data file stored in a plain-text format that a user can open and modify using a standard text editor.
  • Index: The number shown beside a patient in the currently displayed list, starting from 1. Commands use it to refer to a specific patient. A patient's index can change when the displayed list changes, e.g., after a search or a deletion.
  • JAR file: A Java Archive file. MediConnect is distributed as a single JAR file, which can be run on any computer with Java installed.
  • MED_INDEX: The number shown beside a medication in the numbered medication list of the patient's details, starting from 1. editmed and deletemed use it, together with the patient's index, to refer to a medication. It can change when a medication before it is deleted.
  • Medication: A drug prescribed to a patient, recorded with a description (e.g., Metformin 500mg) and its daily times (e.g., 08:00 and 20:00).
  • MSS (Main Success Scenario): The sequence of steps in a use case that describes the most straightforward interaction, in which nothing goes wrong.
  • NRIC: The identification number on a Singapore National Registration Identity Card, or a Foreign Identification Number (FIN), in the format of 1 letter, 7 digits, and 1 letter (e.g., S1234567A). MediConnect uses the NRIC to tell patients apart, since two patients can have the same name.
  • Patient: A person whose care is coordinated using MediConnect, typically an elderly or chronically ill person.
  • Patient profile: The record of a patient in MediConnect. It consists of the patient's basic details (name, NRIC, date of birth, phone number, and address) and their care information.
  • Sample data: Example patient profiles that MediConnect displays when it is launched for the first time, so that new users can see what a complete record looks like.
